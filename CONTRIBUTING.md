# Contributing Guidelines

Welcome! We're glad that you would like to contribute to MuseScore. You can contribute in various ways:

## Testing: reporting bugs and issues
Please find instructions for downloading the latest test builds at [Downloading and running test builds](https://github.com/musescore/MuseScore/wiki/Downloading-and-running-test-builds).
If you have found a bug or issue, please let us know! You can find the preferred way to do this at [Reporting bugs and issues](https://github.com/musescore/MuseScore/wiki/Reporting-bugs-and-issues).

## Development: fixing bugs or building features

We see contributing to development as a process of building a working relationship between the contributor and maintainers. The best way of doing this is for contributors to start small (typically with issues tagged “[good first issue](https://github.com/musescore/MuseScore/issues?q=is%3Aopen+label%3A%22good+first+issue%22)”, “[good second issue](https://github.com/musescore/MuseScore/issues?q=is%3Aopen+label%3A%22good+second+issue%22)”, and "[community](https://github.com/musescore/MuseScore/issues?q=is%3Aopen+label%3Acommunity)") demonstrating solid project knowledge as they build up to larger tasks. Generally speaking, large PRs from newer contributors are not accepted as it is hard for maintainers to verify that the changes have been given the proper care and attention.

It is always recommended to comment asking whether a given issue is free before jumping in with an implementation. This gives the maintainers an opportunity to advise the contributor on implementation/design details, and avoids the possibility of multiple people working on an issue at once.

If you're new to the process of fixing bugs and managing pull requests, you can check out our [suggested Git workflow](https://musescore.org/en/handbook/developers-handbook/finding-your-way-around/git-workflow) and our step-by-step guidance on [setting up a developer environment](https://github.com/musescore/MuseScore/wiki/Set-up-developer-environment). Our [Architecture Design Record](https://github.com/musescore/muse_framework/tree/main/docs/adr) provides context around some of the higher-level, "structural" aspects of the codebase.

When you're ready to open a PR, please ensure that:
- The [Code Guidelines](https://github.com/musescore/dev-docs/blob/main/CodeGuidelines.md) have been followed
- You have read and understood our [AI/LLM Usage Policy for Contributors](https://github.com/musescore/musescore/blob/main/AI_POLICY.md)
- The [Contributor License Agreement](https://musescore.org/cla) has been signed
- The [Contributor Checklist](https://github.com/musescore/MuseScore/blob/main/.github/pull_request_template.md) has been filled out (this is present in the default PR description when opening a PR via the GitHub interface).

Failure to follow the above guidelines may result in your PR being closed.

## Translation
For information about helping to translate and localise MuseScore, please refer to [Help translate MuseScore Studio](https://github.com/musescore/MuseScore/wiki/Help-translate-MuseScore-Studio).

## Offering support to other users
You are welcome to help answering questions from users at the [MuseScore.org forum](https://musescore.org/forum) and in the `#support` channel of our [Discord Server](https://discord.gg/HwHhXEbJ4r).
