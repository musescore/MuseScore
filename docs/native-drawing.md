# Native vector drawing: 4.8 development line

This contribution adds drawing tools to the score view: freehand strokes,
Bezier paths, shapes and arrows, SVG import, editable text and musical
characters, selection, transformations, and point editing. Drawing mode
keeps its input separate from normal music editing.

SVG images and editable drawing data are stored in the score file. Musical
attachments use notes, rests or rhythmic subdivisions. The implementation
includes system-break continuation, undo/redo, linked parts, and painting
with gradients. Playback instructions are not generated by drawings.

## Base and validation

The fork's `drawing-4.8` branch identifies the development line as
`4.8.0-dev`. This numbering identifies this fork's work; an official release
target remains a maintainer decision. The loading screen retains the
original artwork, layout and branding.

The source includes the official `4.7` maintenance branch through the
revision recorded in `native-drawing-upstream.json`. Future maintenance
changes are integrated only after maintainer acceptance and successful
required upstream checks. Open pull requests and unvalidated feature
branches are excluded. Dependencies between accepted changes must be
preserved; an incomplete batch is deferred rather than partially applied.

Acceptance upstream does not establish compatibility with this fork.
When an accepted change conflicts with drawing functionality, compatibility
fixes may change either the drawing implementation or the imported upstream
code. Preserve the intended behaviour of the accepted fix as well as the
fork's drawing behaviour and responsiveness. Add regression coverage for
both sides, and record fork-specific compatibility changes separately from
the original upstream changes. Do not discard an upstream fix merely to
make the drawing checks pass.

When the official 4.7.6 tag becomes available, compare its entire ancestry
and source tree with the recorded baseline. Incorporate outstanding fixes
and additions, preserve the fork's development version, and run the fork's
checks and full build before declaring the integration validated. Do not
mark a build as approved while layout, persistence or parts checks remain
pending. Keep the 5.x port separate from this line.

This is a draft implementation for evaluation. Successful editor checks
do not establish full application, score-file, PDF, part-extraction or
cross-platform compatibility. A complete build and score-level validation
are still required. Rendering and round-trip preservation in unmodified
MuseScore releases need further validation.

## Editor checks

With Qt Quick Test available, run from the repository root:

```sh
qmltestrunner -platform offscreen -input src/notationscene/tests/drawing
```

The checks cover drawing completion, selection movement, undo/redo,
erasing, duplication, grouping, gradients, and input outside drawing mode.
They run against the editor sources used by the native score view.

The `Drawing 4.8` GitHub Actions workflow runs these checks before invoking
the existing Windows portable build workflow. It uses standard hosted
runners and keeps downloadable artifacts for one day. New pushes cancel
obsolete runs of that workflow. Existing upstream pull-request workflows
provide the other platform builds when enabled.
